Diagnosis

The download fully succeeded. Only the final "Download Complete" MessageBox threw.

Look at the tail of your log:

```
[08:54:16.487] Merging 27 chunk file(s)...
[08:54:23.197] SAVED 29635.7 KB (~267876 rows)
[08:54:23.257] Download failed: Error formatting a string: Index (zero based) must be greater than or equal to zero and less than the size of the argument list..
```

· Merging 27 chunk file(s) — all 27 downloaded (no WARNING line about failed chunks)
· SAVED 29635.7 KB (~267876 rows) — merged file written, correct size
· Then the next statement throws → lands in catch → logged as "Download failed"

Your CSV on disk is complete and correct. The scary red message is a lie produced by a string-formatting bug.

---

The bug

The success MessageBox:

```powershell
$ans = [System.Windows.Forms.MessageBox]::Show(
    ("Downloaded:`r`n{0}`r`n`r`nSize: {1:N1} KB`r`n`r`n" +
     "Yes — open the file`r`nNo — open the containing folder`r`nCancel — do nothing") -f `
        $f.FullName, ($f.Length/1KB),
    "Download Complete", 'YesNoCancel', 'Information')
```

The -f operator binds to only $f.FullName — not to ($f.Length/1KB) — because the comma after ($f.Length/1KB) is being parsed as a MessageBox::Show argument separator, not as part of -f's right-hand operand list. So PowerShell evaluates:

· Show arg 1: ("..." + "...") -f $f.FullName  ← -f with one value
· Show arg 2: ($f.Length/1KB)
· Show arg 3: "Download Complete"
· Show arg 4: 'YesNoCancel'
· Show arg 5: 'Information'

The format string contains {1:N1}. String.Format receives only $f.FullName (one value, at index 0), so {1} has no matching argument → the exact exception you saw. MessageBox::Show was never even called — the exception fired while building arg 1.

Precedence inside a method argument list is not intuitive here: -f is a binary operator, but , inside Method(...) is the argument-list delimiter. The parser treats the first comma as ending -f's right operand.

---

Fix

Precompute the string. One line either way, but precomputing removes all doubt:

```powershell
$successMsg = (
    "Downloaded:`r`n{0}`r`n`r`nSize: {1:N1} KB`r`n`r`n" +
    "Yes — open the file`r`nNo — open the containing folder`r`nCancel — do nothing"
) -f $f.FullName, ($f.Length/1KB)

$ans = [System.Windows.Forms.MessageBox]::Show(
    $successMsg,
    "Download Complete",
    [System.Windows.Forms.MessageBoxButtons]::YesNoCancel,
    [System.Windows.Forms.MessageBoxIcon]::Information)
```

If you want to keep it inline, extra parens around the whole -f expression also work:

```powershell
$ans = [System.Windows.Forms.MessageBox]::Show(
    (("Downloaded:`r`n{0}`r`n`r`nSize: {1:N1} KB`r`n`r`n" +
      "Yes — open the file`r`nNo — open the containing folder`r`nCancel — do nothing") -f
      $f.FullName, ($f.Length/1KB)),
    "Download Complete", 'YesNoCancel', 'Information')
```

Precomputing is clearer — that's the form to keep.

One more thing in your log

Look at the gap around chunk 23:

```
<blank lines + "Writing web request" + "Number of bytes written: 443931">

[08:52:25.762]   csv POST (1866 chars of SQL)              ← chunk 24's csv
[08:52:51.428]   OK 1138922 bytes -> ...chunk23.csv       ← chunk 24's OK
[08:52:51.674] Chunk 25/27: 2026-09-21..2026-10-04       ← chunk 25 header
```

Chunk 23's (0-indexed chunk22.csv) csv POST line, OK line, and the Chunk 24/27: header are all missing from the paste. Same 443931-byte partial count as chunk 5's stall, so chunk 23's CSV POST likely also timed out and silently retried successfully — but every Write-DlLog line in that window got overwritten by PowerShell's built-in Write-Progress output from inside Invoke-WebRequest (Writing web request, Writing request stream...). Those are not your log lines — they have no timestamp prefix — they're PS 5.1's progress stream clobbering the console.

The merge confirms 27 chunks were consumed, so nothing was actually lost. But this is exactly why the $ProgressPreference = 'SilentlyContinue' fix I mentioned earlier is worth applying: it stops Invoke-WebRequest from emitting those progress writes at all, so your log stays readable and you can actually tell whether a chunk succeeded, retried, or failed.

---

Full set of edits

Three changes; all cosmetic in effect, but they turn a "download failed" scare into a clean run:

```powershell
# 1. Top of script — kill Invoke-WebRequest progress chatter
$ErrorActionPreference = 'Stop'
$ProgressPreference    = 'SilentlyContinue'   # NEW

# 2. Success MessageBox — precompute the formatted string
$successMsg = (
    "Downloaded:`r`n{0}`r`n`r`nSize: {1:N1} KB`r`n`r`n" +
    "Yes — open the file`r`nNo — open the containing folder`r`nCancel — do nothing"
) -f $f.FullName, ($f.Length/1KB)
$ans = [System.Windows.Forms.MessageBox]::Show(
    $successMsg, "Download Complete", 'YesNoCancel', 'Information')

# 3. Catch block — distinguish "success with a follow-up problem" from a real failure
#    Optional, but nice: if the file exists and is non-empty, don't label it a failure.
```

For #3, if you want the belt-and-suspenders version:

```powershell
} catch {
    if ($script:CancelRequested) {
        ...
    } elseif ((Test-Path $eorFile) -and (Get-Item $eorFile).Length -gt 100) {
        # Something went wrong AFTER the file was written (formatting, etc.)
        $lblStatus.Text = "Saved (UI warning — see log)"
        $lblStatus.ForeColor = [System.Drawing.Color]::DarkGoldenrod
        Write-DlLog "File is on disk, but the completion dialog failed: $($_.Exception.Message)" -Level Warn
    } else {
        # real failure path as before
    }
}
```

Not required — the formatting fix alone is enough. But it means any future "file saved, then this threw" situation won't panic the user.
